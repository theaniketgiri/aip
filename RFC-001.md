## 1. Introduction

### 1.1 Problem Statement

Autonomous AI agents are deployed in production environments with the
ability to execute consequential actions: transferring funds, sending
communications, modifying data, and invoking external services. No
standardized mechanism exists to verify an agent's identity, declared
intent, or authorization boundaries prior to action execution.

Existing approaches are insufficient:

| Approach | Limitation |
|---|---|
| API Keys / OAuth | Authenticates the **caller**, not the **intent**. A compromised or hallucinating agent with valid credentials can act outside its mandate. |
| RBAC / IAM | Static permission sets. Agents require dynamic, per-action, context-aware boundary enforcement. |
| Human-in-the-loop | Negates autonomy. Cannot scale to high-throughput agent interactions. |
| Prompt engineering | "Do not perform unauthorized actions" is not a security boundary. |
| Output filters / guardrails | Post-execution. The unauthorized action has already been attempted or completed. |

### 1.2 Solution

AIP-1 defines a pre-execution verification protocol. Before an agent
acts, it constructs a cryptographically signed **Intent Envelope**
declaring the intended action, target, and parameters. The receiving
party verifies this envelope against the agent's declared **Boundaries**
through a deterministic **Verification Pipeline**.

AIP-1 is:

- **Pre-execution**: Verification occurs before action execution, not after.
- **Cryptographic**: Ed25519 digital signatures provide non-repudiation.
- **Framework-agnostic**: Compatible with any agent runtime.
- **Vendor-neutral**: No dependency on any model provider or platform.

### 1.3 Scope

This specification defines:

- Agent identity format and key material
- Intent Envelope structure and signing
- Verification Pipeline steps and ordering
- Tiered verification for latency optimization
- Revocation and suspension semantics
- Trust score computation model
- Replay protection mechanism
- Error code taxonomy

This specification does NOT define:

- Agent construction or training
- Model inference behavior
- Network transport protocol
- Discovery or routing of agents
- Consensus mechanisms for distributed verification

## 2. Terminology

**Agent**: An autonomous software entity capable of executing actions
on behalf of a principal. An agent possesses a cryptographic identity
and operates within declared boundaries.

**Principal**: The human or organizational entity ultimately responsible
for an agent's actions. The principal delegates authority to the agent.

**Agent Passport**: A data structure containing the agent's identity,
cryptographic key material, boundary declarations, and attestation
metadata.

**Intent Envelope**: A signed data structure declaring an agent's
intended action, target, parameters, and boundary proof prior to
execution.

**Verification Pipeline**: An ordered sequence of checks applied to an
Intent Envelope to determine whether the declared intent is authorized.

**Boundary Cage**: The set of constraints placed on an agent: allowed
actions, denied actions, monetary limits, geographic restrictions, and
time windows.

**Revocation**: The permanent invalidation of an agent's authorization.

**Suspension**: The temporary invalidation of an agent's authorization,
with an expiration timestamp.

**Trust Score**: A numeric value in [0.0, 1.0] representing an agent's
earned trustworthiness based on behavioral history.

**Verifier**: Any party that validates an Intent Envelope before
permitting the declared action to proceed.

## 3. Protocol Overview

The AIP-1 protocol operates in four phases:

```
Phase 1: IDENTITY     Agent possesses a Passport with keypair + boundaries
Phase 2: DECLARATION   Agent constructs and signs an Intent Envelope
Phase 3: VERIFICATION  Verifier validates the envelope through the pipeline
Phase 4: EXECUTION     Action proceeds only if verification passes
```

The protocol flow:

```
┌──────────┐     Intent Envelope      ┌──────────┐
│          │ ──────────────────────▶   │          │
│  Agent   │   (signed, bounded)      │ Verifier │
│          │ ◀──────────────────────   │          │
└──────────┘    Accept / Reject       └──────────┘
                  + Error Code              │
                                            ▼
                                     ┌──────────┐
                                     │ Execute  │
                                     │ or Deny  │
                                     └──────────┘
```

## 4. Agent Passport

### 4.1 Identity

Every agent MUST possess a unique identity conforming to the W3C
Decentralized Identifier (DID) specification, using the `did:web` method:

```
did:web:<domain>:agents:<agent-name>
```

Example:
```
did:web:acme-corp.com:agents:procurement-v1
```

The domain component MUST be a valid DNS hostname controlled by the
agent's principal.

### 4.2 Key Material

An Agent Passport MUST contain:

- **Private Key**: An Ed25519 private key (RFC 8032) used to sign
  Intent Envelopes. The private key MUST be stored securely and
  MUST NOT be transmitted in any protocol message.

- **Public Key**: The corresponding Ed25519 public key, encoded as
  raw 32-byte base64url. The public key MAY be distributed to any
  verifier.

Implementations MUST use Ed25519 as defined in RFC 8032. Other
signature algorithms are not permitted in AIP-1.

### 4.3 Boundary Cage

An Agent Passport MUST declare a Boundary Cage containing:

| Field | Type | Required | Description |
|---|---|---|---|
| `allowed_actions` | `string[]` | REQUIRED | Exhaustive list of actions the agent is authorized to perform. |
| `denied_actions` | `string[]` | OPTIONAL | Actions the agent is explicitly prohibited from performing. Takes precedence over `allowed_actions`. |
| `monetary_limit.per_transaction` | `float` | OPTIONAL | Maximum monetary value per single action, in `currency`. |
| `monetary_limit.per_day` | `float` | OPTIONAL | Maximum cumulative monetary value per 24-hour rolling window. |
| `monetary_limit.currency` | `string` | OPTIONAL | ISO 4217 currency code. Default: `"USD"`. |
| `geo_restriction` | `string` | OPTIONAL | ISO 3166-1 alpha-2 country code. If set, requests from other geographies MUST be rejected. |
| `time_window.start` | `datetime` | OPTIONAL | Earliest time the agent may operate (UTC). |
| `time_window.end` | `datetime` | OPTIONAL | Latest time the agent may operate (UTC). |
| `data_access` | `string[]` | OPTIONAL | Data scopes the agent may access. |

If both `allowed_actions` and `denied_actions` contain the same action,
the `denied_actions` entry MUST take precedence (deny-by-default).

### 4.4 Attestation

An Agent Passport MAY include attestation metadata:

| Field | Type | Description |
|---|---|---|
| `method` | `enum` | One of: `self_reported`, `framework_registry`, `third_party_audit`. |
| `framework_id` | `string` | DID of the agent framework (e.g., `did:web:langchain.com`). |
| `model_hash` | `string` | SHA-256 hash of the model weights or configuration. |
| `system_prompt_hash` | `string` | SHA-256 hash of the system prompt template. |

Attestation fields are used in Tier 2 verification for drift detection.

### 4.5 Delegation Chain

An Agent Passport MUST include at least one delegation link from the
principal to the agent:

```json
{
  "from": "did:web:acme-corp.com",
  "to": "did:web:acme-corp.com:agents:procurement-v1",
  "scope": "procurement",
  "boundary_monotonicity": true,
  "granted_at": "2026-01-15T00:00:00Z",
  "expires_at": "2027-01-15T00:00:00Z"
}
```

**Boundary Monotonicity**: When `boundary_monotonicity` is `true`, a
delegated agent MUST NOT possess broader boundaries than its delegator.
This property MUST be enforced transitively across the delegation chain.

## 5. Intent Envelope

### 5.1 Structure

An Intent Envelope MUST contain the following fields:

```json
{
  "protocol_version": "AIP-1",
  "agent": {
    "id": "did:web:acme-corp.com:agents:procurement-v1",
    "version": "1.0.0",
    "runtime": "aip-sdk/0.1.0",
    "attestation": {
      "method": "framework_registry",
      "framework_id": "did:web:langchain.com"
    }
  },
  "principal": {
    "type": "organization",
    "id": "did:web:acme-corp.com",
    "delegation_chain": [ ... ]
  },
  "intent": {
    "action": "transfer_funds",
    "target": "did:web:vendor.com:agents:billing",
    "parameters": {
      "amount": 45.00,
      "currency": "USD"
    }
  },
  "boundaries": {
    "allowed_actions": ["transfer_funds", "read_invoice"],
    "denied_actions": [],
    "monetary_limit": {
      "per_transaction": 500.00,
      "per_day": 5000.00,
      "currency": "USD"
    },
    "geo_restriction": "US"
  },
  "proof": {
    "type": "Ed25519Signature2024",
    "created": "2026-02-14T10:30:00Z",
    "proof_value": "<base64-encoded-signature>"
  },
  "verification_tier": "tier_1",
  "expires_at": "2026-02-14T11:30:00Z",
  "entropy": "<128-bit-random-nonce-hex>"
}
```

### 5.2 Signing

The signing procedure:

1. Construct the envelope with all fields EXCEPT `proof.proof_value`.
2. Serialize the envelope to a canonical JSON byte string (keys sorted,
   no whitespace, UTF-8 encoded).
3. Compute the Ed25519 signature over the serialized bytes using the
   agent's private key.
4. Set `proof.proof_value` to the base64url encoding of the signature.

Verifiers MUST reconstruct the canonical byte string using the same
serialization rules before verifying the signature.

### 5.3 Verification Tier Selection

The `verification_tier` field MUST be set by the envelope creator
based on the following criteria:

| Condition | Tier |
|---|---|
| Action in same session, same target, amount < 10% of limit | `tier_0` |
| Standard operation within established relationship | `tier_1` |
| First contact with target, cross-org, amount > 50% of limit | `tier_2` |

Verifiers MAY escalate the tier (e.g., from `tier_0` to `tier_1`)
but MUST NOT de-escalate.

## 6. Verification Pipeline

### 6.1 Step Ordering

The Verification Pipeline consists of 8 steps, applied in strict order.
If any step fails, the pipeline MUST halt and return the corresponding
error code. Subsequent steps MUST NOT be executed after a failure.

```
Step 1: VERSION_CHECK        [All Tiers]
Step 2: SCHEMA_VALIDATION    [All Tiers]
Step 3: EXPIRY_CHECK         [All Tiers]
Step 4: REPLAY_DETECTION     [All Tiers]
Step 5: SIGNATURE_CHECK      [All Tiers — method varies by tier]
Step 6: BOUNDARY_CHECK       [All Tiers]
Step 7: REVOCATION_CHECK     [All Tiers]
     ── Tier 0 stops here ──
Step 8: ATTESTATION_VERIFY   [Tier 1, Tier 2]
Step 9: REVOCATION_DEEP      [Tier 1, Tier 2]
     ── Tier 1 stops here ──
Step 10: INTENT_DRIFT        [Tier 2 only]
Step 11: DELEGATION_CHECK    [Tier 2 only]
Step 12: TRUST_EVALUATION    [Tier 2 only]
```

### 6.2 Step Definitions

**Step 1 — VERSION_CHECK**: The `protocol_version` field MUST equal
`"AIP-1"`. Unknown versions MUST be rejected with `AIP-E104`.

**Step 2 — SCHEMA_VALIDATION**: The envelope MUST conform to the
schema defined in Section 5.1. Missing required fields MUST be
rejected with `AIP-E103`.

**Step 3 — EXPIRY_CHECK**: If `expires_at` is present, the current
UTC time MUST be before the expiration timestamp. Expired envelopes
MUST be rejected with `AIP-E101`.

**Step 4 — REPLAY_DETECTION**: The `entropy` value MUST NOT have been
previously observed by this verifier within the replay window (see
Section 10). Duplicate nonces MUST be rejected with `AIP-E102`.

**Step 5 — SIGNATURE_CHECK**: The `proof.proof_value` MUST be a valid
signature over the canonical envelope payload.

- **Tier 0**: If a shared HMAC key has been established (see Section
  7.2), the verifier MAY use HMAC-SHA256 verification. Otherwise,
  Ed25519 MUST be used.
- **Tier 1, Tier 2**: Ed25519 verification MUST be used.

Invalid signatures MUST be rejected with `AIP-E100`.

**Step 6 — BOUNDARY_CHECK**: The declared `intent.action` MUST satisfy:
1. The action MUST be present in `boundaries.allowed_actions`.
2. The action MUST NOT be present in `boundaries.denied_actions`.
3. If `intent.parameters` contains an `amount` field and
   `monetary_limit.per_transaction` > 0, the amount MUST NOT exceed
   the per-transaction limit.
4. If `geo_restriction` is set, the request geography MUST match.

Violations MUST be rejected with the appropriate `AIP-E2xx` error.

**Step 7 — REVOCATION_CHECK**: The agent's `id` MUST be checked
against the revocation registry. Revoked agents MUST be rejected with
`AIP-E400`. Suspended agents MUST be rejected with `AIP-E401`.

This check MUST be performed at ALL tiers, including Tier 0.
Revocation is a security-critical operation that MUST NOT be bypassed
by the fast path.

**Step 8 — ATTESTATION_VERIFY** (Tier 1+): If the agent declares a
`framework_id`, the verifier SHOULD confirm the framework is
registered. If `model_hash` or `system_prompt_hash` are declared,
the verifier SHOULD compare against known values.

**Step 10 — INTENT_DRIFT** (Tier 2 only): The verifier SHOULD apply
a semantic classifier to determine whether the declared action is
consistent with the agent's `allowed_actions` scope. Actions that
are semantically outside the declared scope SHOULD be rejected with
`AIP-E303`.

**Step 11 — DELEGATION_CHECK** (Tier 2 only): The delegation chain
MUST be validated:
1. Each link MUST have a valid `granted_at` and non-expired
   `expires_at`.
2. If `boundary_monotonicity` is `true`, each delegate's boundaries
   MUST be a subset of the delegator's boundaries.

**Step 12 — TRUST_EVALUATION** (Tier 2 only): The verifier SHOULD
compute the agent's trust score (see Section 9). If the score falls
below the verifier's configured minimum threshold, the envelope
SHOULD be rejected with `AIP-E404`.

## 7. Tiered Verification

### 7.1 Rationale

Full cryptographic verification on every intent introduces latency
that may be unacceptable for high-frequency, low-risk interactions.
AIP-1 defines three verification tiers to balance security and
performance.

### 7.2 Tier Definitions

**Tier 0 — Fast Path** (target: <1ms)

- Signature: HMAC-SHA256 (pre-shared key) or Ed25519
- Checks: Version, schema, expiry, replay, signature, boundary,
  revocation
- Use case: Repeated low-risk actions within an established session

Tier 0 MAY use HMAC-SHA256 instead of Ed25519 for signature
verification. The HMAC key MUST be established through a prior
Tier 1 or Tier 2 handshake. The key exchange procedure:

1. Agent and verifier complete a successful Tier 1 verification.
2. Verifier generates a 256-bit random HMAC key.
3. Verifier transmits the HMAC key encrypted with the agent's
   Ed25519 public key (X25519 key agreement).
4. Subsequent interactions within the session MAY use the HMAC key
   for Tier 0 verification.

HMAC keys MUST be ephemeral and MUST NOT persist beyond the session.

**Tier 1 — Standard** (target: ~5ms)

- Signature: Ed25519
- Checks: All Tier 0 checks + attestation verification +
  deep revocation check
- Use case: Normal business operations

**Tier 2 — Full Pipeline** (target: ~50-100ms)

- Signature: Ed25519
- Checks: All Tier 1 checks + intent drift detection +
  delegation chain validation + trust score evaluation
- Use case: High-value transactions, first contact,
  cross-organization interactions

### 7.3 Tier Escalation

Verifiers MAY escalate the verification tier:

- A Tier 0 envelope MAY be verified at Tier 1 or Tier 2.
- A Tier 1 envelope MAY be verified at Tier 2.
- A verifier MUST NOT de-escalate (verify a Tier 2 envelope at Tier 0).

## 8. Revocation and Suspension

### 8.1 Revocation Registry

Implementations MUST maintain a revocation registry mapping agent
identifiers to revocation records. The registry MAY be local (single
verifier) or shared (verification mesh).

### 8.2 Revocation Record

```json
{
  "agent_id": "did:web:acme-corp.com:agents:procurement-v1",
  "reason": "anomalous_behavior_pattern",
  "revoked_at": "2026-02-14T10:45:00Z",
  "revoked_by": "did:web:acme-corp.com",
  "scope": "global",
  "suspended_until": null
}
```

| Field | Type | Description |
|---|---|---|
| `agent_id` | `string` | REQUIRED. The DID of the revoked agent. |
| `reason` | `string` | REQUIRED. Machine-readable reason for revocation. |
| `revoked_at` | `datetime` | REQUIRED. UTC timestamp of revocation. |
| `revoked_by` | `string` | REQUIRED. DID of the revoking party. |
| `scope` | `string` | REQUIRED. `"global"` or `"organization"`. |
| `suspended_until` | `datetime\|null` | OPTIONAL. If non-null, this is a suspension (temporary) rather than a revocation (permanent). |

### 8.3 Semantics

- **Revocation** (`suspended_until` is `null`): The agent is
  permanently invalidated. All subsequent Intent Envelopes from this
  agent MUST be rejected with `AIP-E400`.

- **Suspension** (`suspended_until` is non-null): The agent is
  temporarily invalidated. Intent Envelopes MUST be rejected with
  `AIP-E401` until the current UTC time exceeds `suspended_until`.

- **Reinstatement**: A revoked or suspended agent MAY be reinstated
  by removing its record from the registry. Reinstatement SHOULD be
  logged for audit purposes.

### 8.4 Propagation

This specification does NOT guarantee "zero propagation delay" for
revocation across distributed verifiers. In a distributed deployment:

- Revocation MUST be checked synchronously against the authoritative
  registry at verification time.
- Implementations SHOULD ensure that revocation data is no more than
  `max_staleness_ms` milliseconds old (default: 500ms).
- If revocation data is staler than `max_staleness_ms`, the verifier
  SHOULD return `AIP-E501` (Revocation Stale).

### 8.5 Compromise Handling

If an agent's private key is compromised:

1. The agent MUST be immediately revoked via the revocation registry.
2. All verifiers MUST reject envelopes signed by the compromised key
   upon their next revocation check.
3. A new Agent Passport MUST be issued with a fresh keypair.
4. The compromised agent's DID SHOULD be permanently retired and
   MUST NOT be reused.
5. The principal SHOULD issue a signed Compromise Notice including
   the compromised agent's DID, the timestamp of detection, and the
   replacement agent's DID.

## 9. Trust Score Computation

### 9.1 Definition

The Trust Score is a value in [0.0, 1.0] computed per-agent,
per-verifier. Trust is local — there is no global trust authority.
Each verifier maintains its own trust state.

A score of 0.0 indicates no established trust. A score of 1.0
indicates maximum trust. The default minimum threshold for Tier 2
verification is 0.3.

### 9.2 Computation

The Trust Score is a weighted sum of six components:

$$
T(a) = w_1 \cdot C(a) + w_2 \cdot V(a) + w_3 \cdot R(a) + w_4 \cdot S(a) + w_5 \cdot D(a) + w_6 \cdot A(a)
$$

Where:

| Symbol | Weight | Component | Formula |
|---|---|---|---|
| $C(a)$ | $w_1 = 0.35$ | **Completion Rate** | $\frac{\text{successful\_intents}}{\text{total\_intents}}$ |
| $V(a)$ | $w_2 = 0.25$ | **Violation Rate** (inverted) | $1 - \frac{\text{boundary\_violations}}{\text{total\_intents}}$ |
| $R(a)$ | $w_3 = 0.15$ | **Revocation Penalty** | $\max(0,\ 1 - 0.3 \times \text{revocation\_count})$ |
| $S(a)$ | $w_4 = 0.10$ | **Attestation Stability** | $\max(0,\ 1 - 0.15 \times \text{attestation\_changes})$ |
| $D(a)$ | $w_5 = 0.05$ | **Delegation Depth Penalty** | $\max(0,\ 1 - 0.2 \times (\text{delegation\_depth} - 1))$ |
| $A(a)$ | $w_6 = 0.10$ | **Age Bonus** | $\min(1,\ \frac{\text{total\_intents}}{100})$ |

### 9.3 Properties

- An agent with zero history has a score of 0.0. New agents MUST
  pass Tier 2 verification on first contact regardless of score.
- Each successful verification increases the score. Each boundary
  violation decreases it.
- A single revocation reduces $R(a)$ by 0.3. Three revocations
  reduce $R(a)$ to 0.0.
- The score is bounded: $T(a) \in [0.0,\ 1.0]$.
- Trust scores are non-normative in Tier 0 and Tier 1. They are
  evaluated only in Tier 2 verification.

### 9.4 Adversarial Resistance

The trust model is resistant to the following manipulation strategies:

- **Trust farming**: The age bonus ($A$) is capped at 1.0 and weighted
  at only 0.10. An attacker farming trust through many small
  transactions gains limited advantage.
- **Sybil attacks**: Trust is bound to a DID controlled by a DNS
  domain. Creating new identities requires DNS control.
- **Trust recovery after violation**: The violation rate ($V$) is
  cumulative. A single violation against 10 interactions reduces the
  score significantly. Recovery requires many clean interactions.

## 10. Replay Protection

### 10.1 Nonce Requirements

The `entropy` field in an Intent Envelope MUST satisfy:

1. **Length**: MUST be at least 128 bits (32 hexadecimal characters).
2. **Randomness**: MUST be generated using a cryptographically secure
   random number generator (CSPRNG).
3. **Uniqueness**: MUST be unique per envelope. The probability of
   collision MUST be negligible ($< 2^{-64}$).

### 10.2 Verifier State

Each verifier MUST maintain a nonce cache:

- **Storage duration**: Nonces MUST be stored for at least the
  maximum envelope TTL (default: 3600 seconds / 1 hour).
- **Scope**: Nonce uniqueness is per-verifier, not global. Two
  different verifiers MAY independently accept the same nonce.
- **Eviction**: Nonces older than the storage duration MAY be evicted.
- **Capacity**: Implementations SHOULD support at least 1,000,000
  concurrent nonces.

### 10.3 Distributed Replay Detection

In a managed verification mesh, replay detection MAY be extended
across verifiers:

- A centralized nonce registry receives nonces from all verifiers.
- Before accepting an envelope, a verifier queries the registry.
- This provides cross-verifier replay protection at the cost of
  an additional network round-trip.

Distributed replay detection is OPTIONAL and is a feature of the
managed verification mesh, not the core protocol.

## 11. Key Management

### 11.1 Key Generation

Agent keypairs MUST be generated using Ed25519 as specified in
RFC 8032. The private key MUST be generated using a CSPRNG.

### 11.2 Key Storage

- Private keys MUST be stored encrypted at rest.
- Private keys MUST NOT be logged, transmitted, or included in
  Intent Envelopes.
- Private keys SHOULD be stored in a hardware security module (HSM)
  or secure enclave in production deployments.

### 11.3 Key Rotation

Agents SHOULD rotate keypairs periodically. The rotation procedure:

1. Generate a new Ed25519 keypair.
2. Create a Key Rotation Envelope signed by the OLD private key,
   containing the new public key.
3. Distribute the Key Rotation Envelope to all known verifiers.
4. After a grace period (RECOMMENDED: 24 hours), retire the old
   public key.
5. Update the Agent Passport with the new public key.

During the grace period, verifiers MUST accept signatures from
either the old or new key.

### 11.4 Key Compromise

See Section 8.5 (Compromise Handling).

## 12. Error Taxonomy

### 12.1 Error Code Format

All AIP errors follow the format `AIP-Exxx` where `xxx` is a
three-digit numeric code. Errors are grouped by category:

### 12.2 Error Codes

**AIP-E1xx — Envelope Errors**

| Code | Name | Description |
|---|---|---|
| `AIP-E100` | `INVALID_SIGNATURE` | Ed25519 or HMAC signature verification failed. |
| `AIP-E101` | `EXPIRED_ENVELOPE` | Current UTC time exceeds `expires_at`. |
| `AIP-E102` | `REPLAY_DETECTED` | Entropy nonce has been previously observed. |
| `AIP-E103` | `SCHEMA_INVALID` | Envelope does not conform to the required schema. |
| `AIP-E104` | `VERSION_UNSUPPORTED` | `protocol_version` is not supported by this verifier. |

**AIP-E2xx — Boundary Violations**

| Code | Name | Description |
|---|---|---|
| `AIP-E200` | `ACTION_NOT_ALLOWED` | `intent.action` is not in `boundaries.allowed_actions`. |
| `AIP-E201` | `ACTION_DENIED` | `intent.action` is in `boundaries.denied_actions`. |
| `AIP-E202` | `MONETARY_LIMIT` | Transaction amount exceeds `monetary_limit.per_transaction` or `monetary_limit.per_day`. |
| `AIP-E203` | `TIME_WINDOW_VIOLATION` | Request is outside the agent's authorized time window. |
| `AIP-E204` | `GEO_RESTRICTION` | Request geography does not match `geo_restriction`. |

**AIP-E3xx — Attestation Failures**

| Code | Name | Description |
|---|---|---|
| `AIP-E300` | `MODEL_HASH_MISMATCH` | Declared `model_hash` does not match the registered value. |
| `AIP-E301` | `PROMPT_HASH_MISMATCH` | Declared `system_prompt_hash` does not match the registered value. |
| `AIP-E302` | `FRAMEWORK_UNREGISTERED` | Declared `framework_id` is not in the attestation registry. |
| `AIP-E303` | `INTENT_DRIFT` | Semantic classifier flagged the action as outside declared scope. |

**AIP-E4xx — Trust and Revocation Failures**

| Code | Name | Description |
|---|---|---|
| `AIP-E400` | `AGENT_REVOKED` | Agent has been permanently revoked. |
| `AIP-E401` | `AGENT_SUSPENDED` | Agent is temporarily suspended (check `suspended_until`). |
| `AIP-E402` | `PRINCIPAL_REVOKED` | The agent's principal organization has been revoked. |
| `AIP-E403` | `DELEGATION_INVALID` | Delegation chain is broken, expired, or violates boundary monotonicity. |
| `AIP-E404` | `TRUST_SCORE_LOW` | Agent trust score is below the verifier's minimum threshold. |

**AIP-E5xx — Protocol Errors**

| Code | Name | Description |
|---|---|---|
| `AIP-E500` | `MESH_UNAVAILABLE` | Cannot reach the verification mesh for distributed checks. |
| `AIP-E501` | `REVOCATION_STALE` | Revocation data exceeds `max_staleness_ms`. |
| `AIP-E502` | `HANDSHAKE_TIMEOUT` | Tier upgrade or key exchange timed out. |

### 12.3 Error Response Format

All error responses MUST include:

```json
{
  "error_code": "AIP-E202",
  "error_name": "MONETARY_LIMIT",
  "description": "Transaction amount exceeds per-transaction monetary limit",
  "detail": "Requested $15,000.00 but boundary allows $500.00 per transaction"
}
```

## 13. Threat Model

### 13.1 Attacker Capabilities

AIP-1 assumes the attacker MAY:

| Capability | Mitigation |
|---|---|
| **Replay captured envelopes** | Nonce-based replay detection (Section 10). Each envelope contains a unique `entropy` value. |
| **Forge envelope signatures** | Ed25519 provides 128-bit security. Forging a valid signature requires the private key. |
| **Modify envelope payloads** | Any modification invalidates the Ed25519 signature. Canonical serialization prevents ambiguity. |
| **Attempt boundary escalation** | Boundaries are embedded in the signed envelope. Modifying boundaries invalidates the signature. |
| **Steal agent private keys** | Compromise handling (Section 8.5): immediate revocation + key retirement. |
| **Manipulate trust scores** | Trust farming is bounded by the weighted model (Section 9.4). Sybil attacks require DNS control. |
| **Exhaust nonce storage** | Implementations SHOULD support ≥1M concurrent nonces and evict expired entries. |
| **Downgrade verification tier** | Verifiers MUST NOT de-escalate tiers. Tier 0 still enforces revocation checks. |

### 13.2 Out of Scope

AIP-1 does NOT protect against:

| Threat | Rationale |
|---|---|
| **Compromised agent runtime** | If the runtime executing the agent is compromised, the attacker has access to the private key. This is a platform security concern, not a protocol concern. |
| **Malicious model output before envelope creation** | AIP verifies the declared intent, not the model's internal reasoning. A model that "decides" to perform a harmful action but declares it correctly will be caught by boundary checks. A model that declares a benign action but internally plans something different is outside AIP's scope. |
| **Denial of service against verifiers** | Rate limiting and resource management are implementation concerns. |
| **Side-channel attacks on cryptographic operations** | Implementations SHOULD use constant-time Ed25519 libraries. |

### 13.3 Trust Assumptions

1. The agent's DNS domain is controlled by the declared principal.
2. The Ed25519 implementation is correct and uses a CSPRNG.
3. The verifier's clock is synchronized to within 1 second of UTC.
4. The revocation registry is available and responsive.

## 14. Security Considerations

### 14.1 Canonicalization

Envelope serialization MUST produce a deterministic byte sequence.
Implementations MUST sort JSON keys alphabetically and MUST NOT
include whitespace. This prevents signature verification failures
due to serialization differences.

### 14.2 Time Synchronization

Expiry checks depend on UTC time. Verifiers with unsynchronized
clocks may incorrectly accept expired envelopes or reject valid
ones. Implementations SHOULD use NTP and SHOULD reject envelopes
with `expires_at` more than 5 seconds in the past (grace period
for clock skew).

### 14.3 Envelope TTL

Envelopes SHOULD have a short TTL. The RECOMMENDED maximum TTL is
3600 seconds (1 hour). Envelopes without an `expires_at` field
SHOULD be treated as expiring in 300 seconds (5 minutes).

### 14.4 Private Key Protection

The security of AIP-1 depends entirely on the secrecy of agent
private keys. Implementations MUST NOT:

- Log private keys
- Include private keys in error messages
- Transmit private keys over unencrypted channels
- Store private keys in plaintext on disk

### 14.5 Post-Quantum Considerations

Ed25519 is not quantum-resistant. When post-quantum signature
schemes are standardized (e.g., NIST PQC), a future version of AIP
SHOULD define a migration path. The `proof.type` field provides
extensibility for alternative signature schemes.

## 15. Framework Compatibility

AIP-1 is designed to be framework-agnostic. The following integration
points exist:

| Framework | Integration Method |
|---|---|
| LangChain / LangGraph | Tool wrapper that creates and signs envelopes before tool execution |
| CrewAI | Agent-level passport, per-task envelope signing |
| AutoGPT | Plugin boundary enforcement via AIP verification |
| Microsoft AutoGen | Message-level envelope verification between agents |
| Custom Python agents | Direct SDK usage: `pip install aip-protocol` |

Framework-specific integration packages (e.g., `aip-langchain`) MAY
provide convenience wrappers but MUST use the core protocol as defined
in this specification.

## 16. Open Questions

The following items are under active discussion:

1. **Cross-organization trust federation**: How SHOULD trust scores
   propagate across organizational boundaries? What trust discount
   applies to cross-org scores?

2. **Delegation chain depth limits**: What is the maximum safe
   delegation chain length? RECOMMENDED limit: 5 levels.

3. **Post-quantum migration**: At what timeline SHOULD AIP migrate
   from Ed25519 to post-quantum signatures?

4. **Regulatory alignment**: How does AIP map to EU AI Act agent
   accountability requirements? What audit export formats are
   needed for compliance?

5. **Monetary limit aggregation**: How SHOULD per-day monetary limits
   be enforced across distributed verifiers that do not share state?
